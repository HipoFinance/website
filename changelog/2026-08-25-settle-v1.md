# 2026-08-25 — Settling protocol v1, by counting it first

Protocol v1 ran on a single contract that was both master and treasury, at a
different address from today's v2 deployment, and it still has holders. It has
been sitting in the migration backlog complicating every v2→v3 discussion, so
the instruction this session was: decide it, either way, and take it off the
table.

The rule going in was **open it by counting, not by writing code**. So the
census came first, the decision second, and only then the deletion.

## What the "upgrade" button actually was

It was a real migration, and better than it looked from the client code alone.
`upgradeOldWallet` sent `opUnstakeTokens` (`0x595f07bc`) with 0.1 GRAM to the
user's _v1 wallet_ — and stopped there, which reads like a plain redemption. The
rest happens on chain. Tracing a completed run (13 May 2025):

```
IN  0x24a319a7  from the v1 wallet    0.0632
   OUT-> owner                         0.0586   gas excess
IN  0x3cfe4dcb  from the v1 wallet    0.2942
   OUT-> 0:8BC991CFE177BC7E97…         1.1579   op 0x3d3761a6
   OUT-> owner                         0.1373   gas excess
```

`0:8BC991CFE177BC7E97…` is the **v2 treasury**
(`EQCLyZHP4Xe8fpchQz76O-_RmUhaVc_9BAoGyJrwJrcbz2eZ`) and `0x3d3761a6` is
`opDepositCoins`. The v1 treasury forwards the redeemed coins into v2 as a
deposit, so one signature carries a holder from hTON1 all the way to minted
hGRAM. The English copy — "After the upgrade, you'll get {new} in the new
version" — was accurate, and the `newWalletTokens` projection beside it was the
amount actually minted.

That is worth stating plainly because it raises the bar for deleting the
feature: what is being removed is a working migration, not a mislabelled
unstake.

## It had been used — just not lately

The working assumption was that nobody had ever used it. Not quite true: seven
distinct owners used it in 2025 — 2 April, 6 April, 13 May, 11 June, 19 June,
11 July, and last on **12 October 2025**. All seven wallets read zero today, so
every attempt succeeded.

That is also the entire tail: the v1 treasury has had **no transaction of any
kind in the ten and a half months since**. But "succeeded" turned out to be too
generous — see _Four holders are stuck mid-migration_ below. Only three of the
seven completed.

## A governor-paid force-migration exists — and it works

An earlier draft of this report claimed there was no way to close v1 without
each holder acting. **That was wrong**, and Behrang remembered the counter-example:
a batch script that pushes holders through the migration with the caller paying
the gas. It is on chain, 96 times over:

```
LEG 1  caller  → v1 treasury     op 0x00000100  0.25 GRAM  body: query_id, owner
       v1 tr.  → holder's wallet op 0x2dda9652  0.2412
       wallet  → v1 treasury     op 0x24a319a7             reserve_tokens
       v1 tr.  → driver          op 0xd53276db  0.204      excess — chain ENDS here
LEG 2  driver  → holder's wallet op 0x469bd91e  0.30       separate, driver-funded
       wallet  → v1 treasury     op 0x3cfe4dcb             burn_tokens
       v1 tr.  → v2 treasury     op 0x3d3761a6             deposit → hGRAM minted
```

Run on 2024-03-19 (5 wallets) and 2024-03-26 (91), it moved **347,469.90 GRAM**
into v2 for **24.30 GRAM of gas — 0.2531 per holder**. All 96 targets are empty
today: a 100 % success rate, no user action, no bounces. The smallest one carried
just 0.15 GRAM, so dust is not an obstacle (`minimumDepositAmount` is a few
nanograms).

Two of the three addresses in v1's storage are the gas-excess recipient
(`EQCxBMeY…`) and, tellingly, the **v2 treasury itself** (`EQCLyZHP…`). That is
not a coincidence: in v1 the `next_treasury` field _replaced_ `halter` in
storage, and `burn_tokens` hardcodes v2's deposit opcode as a literal —
`origin/v1:contracts/treasury.fc:366-374` sends `0x3d3761a6` with the proceeds.
v1 was deliberately patched to empty itself into v2.

**The op has no access control at all.** `origin/v1:contracts/treasury.fc:1515`
dispatches `0x100` ahead of every named op, discards the message's real `src`,
and substitutes the caller-supplied `owner`:

```func
if (op == 0x100) {
    in_msg_body~skip_bits(64);
    slice owner = in_msg_body~load_msg_addr();
    in_msg_body.end_parse();
    return send_unstake_all_tokens(owner);
}
```

and `send_unstake_all_tokens` (`:406-418`) checks only that the owner is on the
basechain — no governor, no halter. Contrast v2's equivalent
(`contracts/treasury.fc:2107`), which does guard on
`equal_slice_bits(src, governor) | equal_slice_bits(src, halter)`. The v1 _wallet_
side (`origin/v1:contracts/wallet.fc:239-261`) accepts `unstake_all_tokens` from
the treasury **only** — never from the owner — and then re-enters
`unstake_tokens` passing `owner` as a synthetic `src`, which is what satisfies
that function's own owner check at `:215`.

So anyone willing to pay the gas can migrate any v1 holder. That explains the 90
pushes from an address that appears nowhere in the contract's state.

### Four holders are stuck mid-migration

The migration is **two** operator messages, not one. Leg 1 (`0x100`) ends at
`reserve_tokens`, which per `origin/v1:contracts/treasury.fc:285-309` dumps all
remaining value to the stored **driver** and stops — the comment there says so:
_"send all remaining value to driver for later burning and upgrading to next
treasury"_. Leg 2 is a separate driver-funded push (`0x469bd91e` /
`withdraw_tokens`) that produces `burn_tokens` and the v2 deposit.

The user-initiated button needed leg 2 too — the **driver service** supplied it,
watching for `reserve_tokens` and answering with two externals carrying 0.3 GRAM
each (one usually bounces harmlessly). Its last external action was
**2025-05-13 16:58**; every driver-wallet transaction after that date is passive,
just receiving leg-1 excess. So the driver was retired somewhere between
2025-05-13 and 2025-06-11 — as part of winding v1 down — and nothing was left to
finish the chain. In 2025
`0x24a319a7` fired 7 times but `0x3cfe4dcb` only 3, leaving four people with
`tokens = 0` and their coins parked in `unstaking`:

| wallet        | asked to leave | stuck `unstaking` |
| ------------- | -------------- | ----------------- |
| `0:C9C5D747…` | 2025-06-11     | 0.0195 hTON1      |
| `0:6738FDB7…` | 2025-06-19     | **4.9423** hTON1  |
| `0:706C4E2E…` | 2025-07-11     | 0.9960 hTON1      |
| `0:2954579F…` | 2025-10-12     | 3.1500 hTON1      |

That sums to 9.1077, which is exactly the previously unexplained 9.1078 GRAM at
index 3 of `get_treasury_state`; and `286.276 + 9.108 = 295.384` = total supply.
The whole population reconciles. Freeing them costs 4 × 0.3 GRAM ≈ $1.74.

This also corrects an earlier claim in this report: the last _complete_ migration
was 2025-05-13, not 2025-10-12, and "all seven 2025 attempts succeeded" was wrong
— three did.

**Which settles the case for deleting the dApp button.** From roughly June 2025
the Upgrade button was _broken_: a holder clicked it, paid ~0.1 GRAM, watched
`unstake_tokens` burn their balance into `unstaking` — and then nothing, because
the service that drove the second half no longer existed. The four stuck holders
are precisely the four people who clicked it after the driver went dark. Removing
the button was not housekeeping; it was retiring something that had been quietly
taking money and stranding the few people who trusted it.

### What it costs, measured

The fee floor is **not** frozen. `min_ton = unstake_all_tokens_fee() +
unstake_tokens_fee()` (`origin/v1:contracts/wallet.fc:248`) is price-linear and
read from live network config at execution time — the deployed constants are gas
_amounts_, never gas _prices_. It was ≈ 0.0895 GRAM in March 2024 and is
**≈ 0.01505 GRAM today**, TON's basechain gas and forward prices having fallen
about 6×. The 0.25 push is ~16× the current floor, and `0.25` appears exactly
once, at `origin/v1:scripts/sendUnstakeAllTokens.ts:25` — nothing else pins it.

Leg 2 cannot be cut the same way: `origin/v1:contracts/treasury.fc:342` rejects
`burn_tokens` unless it arrives with **≥ 0.2 GRAM**, frozen into the deployed
treasury, and `:374` prepays a further 0.15 GRAM to the v2 treasury out of that
same push.

|                                         | send       | refunded to driver | net       |
| --------------------------------------- | ---------- | ------------------ | --------- |
| leg 1 `0x100`, at 0.25 (2024, measured) | 0.25       | 0.204              | 0.046     |
| leg 1 `0x100`, at 0.05 (today)          | 0.05       | ~0.04              | ~0.01     |
| leg 2 `0x469bd91e`                      | ~0.25–0.30 | ~0.09–0.14         | ~0.16     |
| **per holder**                          | **~0.30**  | **~0.13**          | **~0.17** |

For 211 holders that is **~36 GRAM of net outlay (~$52)** — and most of it is not
burned. The 0.15 prepay cascades out of the v2 deposit and ~0.13 of it lands in
**the holder's own wallet** as gas excess, so the genuine network burn is only
about **8–10 GRAM (~$13)** in total.

### Could an upgrade make it cheaper? Yes. Not enough to be worth it.

v1 **is** upgradeable: `op::upgrade_code 0x36e4c27d`
(`origin/v1:contracts/treasury.fc:1630-1632`, handler `:1384-1397`), guarded on
`governor` — `EQCG7nRE…`, an ordinary **wallet v3 r2**, seqno 85, balance
0.85 GRAM. That is the same address that sent 6 of the 96 pushes in March 2024,
so the key has been used. Note it is a plain code swap: v1 has **no**
`run_migrator` / `0x6d67` (a v2-only feature), and its `upgrade_data` ignores
`new_data` entirely, so any storage migration would have to be hand-written.

And the collapse to one push is real, for a better reason than "no sender check":
the frozen wallet's `unstake_tokens_fee()` **already pre-pays the whole chain
through `burn_tokens` and the final excess**. The only thing stopping it is
`reserve_tokens` dumping to the driver at `:303-306`. Replace those four lines
with a `withdraw_tokens` send back to the same wallet and one `0x100` drives
everything. The two frozen constants also become editable: `:342`'s 0.2 floor
could go to ~0.005, and `:374`'s 0.15 prepay to ~0.012 (v2's actual
`deposit_coins_fee` is 0.00878).

|                   | today               | after upgrade       |
| ----------------- | ------------------- | ------------------- |
| pushes per holder | 2                   | 1                   |
| sent              | ~0.30               | **0.020**           |
| net per holder    | ~0.17               | **~0.016**          |
| × 211 holders     | **35.9 GRAM ≈ $50** | **3.4 GRAM ≈ $4.7** |

**But the saving is mostly illusory.** Of today's 0.17, **0.15 is the v2 prepay
and ~0.14 of that cascades straight back into the holder's own wallet**. Genuinely
burned gas is ~6.3 GRAM (≈ $9) today versus ~1.7 GRAM (≈ $2.4) after — a real
efficiency gain of about **$7**. The rest of the headline saving is an
over-generous gas gift to the very people being migrated. Even adding the
~10 GRAM that `fee::treasury_storage` makes permanently unsweepable, the ceiling
is ~$60.

Against that: a modified `treasury.fc`, a ported dry-run harness (v1's
`upgradeCode.ts` only prints byte counts and asks for `YES` — none of main's
sandbox diff), a sandbox suite against fetched state, and **one irreversible
governor-signed transaction** on a March-2024 contract holding 320.6 GRAM and
owing 300.2. `recv_internal` calls `load_data()` before dispatch (`:1477`), so
code whose `load_data()` cannot parse the existing cell means **no further
upgrade can ever be received** and the funds are stranded permanently. Roughly
1–3 days of someone who knows this codebase.

**Verdict: abandon the upgrade route.** Run the existing two-message procedure.

One practical detail: refunds go to the **driver address stored in the v1
treasury** (`EQCxBMeY…`), never to whoever paid — `return_excess` is parsed and
then ignored. So the batch should be run _from_ that wallet, where the refunds
recycle into the working float. It currently holds 34.41 GRAM against the
35.9 needed — short by ~1.5, so top it up to ~40 GRAM and it finances the whole
run by itself.

Two more mechanical notes for whoever runs it: the 45 s sleep is far more than
needed (leg 1 completed in 36 s on the slower 2024 chain), and the driver is a
**wallet v4r2**, which carries 4 messages per external — 211 pushes become ~53
externals, turning 2 h 40 m into roughly ten minutes.

None of which changes what this repo should do. v1 holders earn nothing (v1 is
idle; v2 pays ~16.6 % APY), so migrating them is strictly to their benefit — and
once the batch runs, the dApp feature has zero remaining users. Removing it is
right whether or not the batch happens; it just becomes obvious afterwards.

Keeping the feature was also not free:

- Every user who connects a wallet pays an extra v1 get-method round trip,
  forever, to serve 211 dust positions.
- `readOldWallet` was awaited inside `readLastBlock`'s `try`, so a failing v1
  get-method landed in the shared error path — `errorTonAccess`, a timer
  reschedule, and `countTonEndpointFailure()`. A dead legacy contract could
  push the **healthy v2 path** toward an endpoint failover.
- Five translation keys carried across ten locales, plus the sidecar hashes.

So: removed, with the manual recipe below preserved in place of the code.

## Migrating hTON1 by hand

This is now the only path, so it is recorded here and in the session memory. It
produces the same result the button did — hGRAM in v2, not GRAM in the wallet.

1. Call `get_wallet_address(owner_address)` on
   `EQBNo5qAG8I8J6IxGaz15SfQVB-kX98YhKV_mT36Xo5vYxUa` to get the holder's v1
   wallet.
2. From the **owner's** wallet, send **0.1 GRAM** to that address with the body
   `uint32 op = 0x595f07bc`, `uint64 query_id`, `coins tokens` (the full v1
   balance), `address` = `addr_none`, `maybe ref` = null.
3. The v1 treasury redeems and forwards the proceeds to the v2 treasury as an
   `opDepositCoins`; hGRAM is minted to the owner and the gas excess is
   returned. v1 is fully liquid, so there is no round to wait for.

The 211 owner addresses were deliberately **not** committed to this public
repo. Regenerate the census from
`/api/v3/jetton/wallets?jetton_address=<treasury>&limit=1000` (887 records, a
single page) if outreach is ever wanted.

## Outcome — v1 is empty

Executed 2026-08-26 from the driver wallet, in three phases (four stuck holders,
four representative fresh holders to validate the reduced leg-1 value, then the
remaining 207). Final on-chain state of the v1 master/treasury:

|                                     |                            |
| ----------------------------------- | -------------------------- |
| `total_supply`                      | **0**                      |
| `total_coins` / `total_tokens`      | 0 / 0                      |
| `total_staking` / `total_unstaking` | 0 / 0                      |
| holders                             | **none**                   |
| treasury balance                    | 20.359 GRAM, owing nothing |

~291 GRAM went out as hGRAM to 211 wallets, and the four people who had been
stranded mid-migration since June 2025 were made whole.

**Recovering the remainder.** `op::withdraw_surplus 0x302b2fea`
(`origin/v1:contracts/treasury.fc:1399`, guarded on `governor`) computes
`available = balance_before_msg − fee::treasury_storage − validators_stake −
total_staking − total_coins`. Every term but the first two is now zero, so it
returns **10.359 GRAM** and leaves the 10 GRAM floor behind. Note the value sent
_with_ the request stays in the treasury, since `available` is computed before
the message — so it is sent with the minimum that covers gas.

**The last 10 GRAM is not worth chasing.** It would take an upgrade, and while the
risk did drop sharply once the treasury stopped owing anyone anything, the reward
dropped with it. Sweep first and the question becomes: wager the remaining
10 GRAM (~$14.50) to win 10 GRAM (~$14.50), at a cost of 1–3 days. Worse, a
minimal "sweeper" contract is not the easy way out it appears to be — v1's
`upgrade_data` (`:1370-1374`) re-asserts `src == governor` _under the new code_,
so the replacement must still parse the existing storage layout correctly or the
upgrade reverts. That is exactly the subtlety that bricks contracts, and v1 has
none of main's dry-run harness. The 10 GRAM also pays the contract's storage
rent, which keeps it active rather than frozen — and TON's storage prices just
fell ~6×, so it will sit there for a very long time.
